# 01 · 模块设计与规范细则

## 一、为什么必须分层

如果所有变量混在一个文件里，会发生两件事：间距值被随手写成 13、17 这种非刻度值，因为写代码时没有任何东西阻止你；以及修改某个元素尺寸时，无法预知牵动了哪些其他元素。分层就是把「全局纪律」和「局部调整」在物理上隔开。

- **`tokens.ts` 是纪律层**：间距、断点、原点、**颜色、字阶、圆角**。间距强制走刻度 `SPACE = {xs:4, sm:8, md:16, lg:24, xl:48}`。
  强制走刻度的理由不是美观，而是**让间距成为有限集合**——只有这样，「间距一致性」才能被脚本检查。
- **`layout.ts` 是调整层**：页头高度、侧栏宽度这类元素特定尺寸。不受刻度约束，但受注释契约约束。

### 设计 token 与几何 token 同级

```
SPACE / BREAKPOINTS / ORIGIN   → 几何
COLOR / TYPE / RADIUS          → 视觉
```

两者都写进 `variableSnapshot`，渲染器只从快照读。理由和间距刻度一样：
把「好看」拆成有限集合之后，它才能被复制、被评审、被整体替换。
渲染器里出现 `#2563EB` 或 `font-size: 15` 这类硬编码，等同于几何里的裸字面量。

## 二、注释契约

每个变量固定四行注释，恰好覆盖用户改一个变量时最关心的三个问题：

```
作用：    它管什么
影响范围：改它会动哪儿（写元素编号，如「① header 高度；②③ 的 y 坐标」）
可调范围：我能改到多大（如 48 ~ 96px）
```

- 「影响范围」要求写出**元素编号**，不是文档洁癖，而是给修改回路供数据。
- 「可调范围」承担另一项职责：**防止用户提出超出合理区间的修改时 AI 无脑照办**。
  `indexer --impact` 会据此在 diff 预览里加一行 `⚠ 超出可调范围`。
- tokens 额外要求 `可选值` 或 `临界参数`。

## 三、命名约定是给静态分析留的信号

几何变量强制全大写下划线（`HEADER_H`）。约定本身不值钱，**约定带来的可分析性才值钱**：

- `indexer` 用 `^[A-Z][A-Z0-9_]+$` 在 AST 里识别几何量，把 `MAX_RETRY = 3` 这类普通常量排除在外；
- `lint-geometry` 用 `(_H|_W|_X|_Y|GAP|PAD|MARGIN|INSET)$` 判断字面量是否落在几何上下文。

## 四、布局计算的三条具体含义

**1. 无副作用**：不读文件、不打日志、不改全局状态。
因为 `assert-layout` 的验证方式之一是「用同一批变量复算一遍，比对两次的树是否完全一致」。

**2. 零几何字面量**：不仅禁止 `88`，还禁止表达式里的 `10`（`A.y + 10` 同样违规）。
要堵到这个程度，是因为「表达式里的 10」是最常见的逃逸通道：模型觉得「就一个小调整值，没必要定义变量」，结果这个数字从此脱离变量体系，用户改 `GAP` 时它纹丝不动。

```
❌ const y = HEADER_H + 10;
✅ const y = HEADER_H + GAP_SM;   // GAP_SM 在 variables/ 里
```

`ORIGIN = 0` 的存在就是为了让「贴边对齐」也有变量出处，而不是裸写 `0`。

**3. 双断点共享一套公式**：这是最容易被写错的地方。

```
❌ 按断点写两套（会随迭代悄悄漂移）
   if (isDesktop) { contentX = SIDEBAR_W + SPACE.md; ... } else { contentX = SPACE.md; ... }

✅ 断点只在构建上下文时起作用，之后公式只有一份
   function context(bp) { return { sidebarW: isDesktop ? SIDEBAR_W_DESKTOP : SIDEBAR_W_MOBILE, ... }; }
   function layout(ctx) { const contentX = ctx.sidebarW + ctx.gapLg; /* 公式不感知断点 */ }
```

`SIDEBAR_W_MOBILE = 0` 是这套做法的关键技巧：公式自然退化，无需分支。
新增平板档时只改 `context()`，公式零改动。

## 五、`expr` 是数据字段，不是注释

```
y: "HEADER_H + SPACE.lg = 64 + 24"
```

- 把结果写成 `64 + 24` 而不是 `88`，是为了让**中间量也留在记录里**；
- 定位图标注显示为 `88px ⟵ HEADER_H + SPACE.lg = 64 + 24`——数字与出处同时呈现；
- `verify-positioning` 把两段**分别**复算，都要求等于树值。只校验一侧会留下逃逸通道。

## 六、验证层：四层 + 一道闸门

> 「四层」是按**阶段**的概念划分；`run-all.mjs` 实际串行**八步**（另含 indexer / check-drawio / docgen），两种口径不矛盾。

| 层 | 脚本 | 判定细节 |
|---|---|---|
| ① 编码期 | `lint-geometry` | 字面量出现在几何关键词上下文即报错；**报错信息自带改法** |
| ② 构建期 | `assert-layout` | 越界 / **兄弟**重叠 / 间距刻度（含快照集合判定）/ expr 完整性 / 纯函数复算 |
| ③ 确认期 | `verify-positioning` | 在确认节点 B **之前**跑，防查看器读错树、防有人手改标注值 |
| ④ 交付期 | `check-env` | `.nvmrc` / 锁文件 / `node_modules` / `.venv` / `globalInstall` 自报 |
| 闸门 | `check-confirmation` | 确认记录存在且指纹未失效，否则直接阻断渲染 |

**重叠只检测兄弟节点**：父子之间的包含关系天然不算重叠；naive 的全局两两检测会把正常嵌套全部误报。

**间距刻度检查的两处落点**：① 相邻兄弟间距必须 ∈ SPACE；② `variableSnapshot` 中名字像间距的变量取值也必须 ∈ SPACE。
第二处是「间距强制走刻度」的执行末端——只查兄弟间距会漏掉「定义了间距变量但没用上」的情况。

## 七、序列化器铁律：零几何计算

```
❌ left: ((node.x / canvas.w) * 100) + "%"
✅ left: node.x            // React 自动补 px；缩放交给 CSS 变量 --layout-scale
```

一旦渲染器里允许几何运算，就存在「树里标的 88、渲染出来是 90」的缝隙，前面所有确认流程的意义都会被架空。

为可追溯，DOM/JSX 产物每个节点挂 `data-layout-id` 与 `data-expr`；
位图无法挂属性，可追溯性由定位图承担，`--annotate` 可把 expr 画在图里。
`pil.py --scale` 是渲染完成后对**整图**重采样（DPI 级），不参与坐标计算。

## 八、两级确认与闸门

- **确认节点 A（结构）**挡方向性错误。成本极低（一棵缩进文本树），但能在变量和代码白写之前拦下。
- **确认节点 B（定位）**挡数值性偏差。

两者都必须**落盘**：

```
positioning/confirmed.json   原始记录 {node, bp, hidden, 时间戳, treeHash, source}
        ↓ indexer 聚合
manifest.confirmations       聚合视图 {structure, positioning: {"<画布名>": bool}, storyboard}
        ↓ 渲染序列化器第一步读取
不通过 → 抛错退出
```

`treeHash` **只对几何载荷**取哈希（canvas + 每个节点的 `{id, depth, x, y, w, h, expr, children}`）：

- 移动 1px、改公式 → 指纹变化 → 必须重新确认；
- 补一句 `note`、加一条 `refs` → 指纹不变 → 不必重新确认。

这条边界是刻意划的：确认表达的是「我认可这套几何」，不是「我认可这版文案」。
另外**修改哈希定义本身会让既有确认全部失效**（fail-closed），这是预期行为。这就是把「AI 说自己确认过了」变成「机器能查的确认记录」。
